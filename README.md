# Face Verification and Blockchain Evidence Registry

## Overview

Face Verification and Blockchain Evidence Registry is an end-to-end system for verifying the identity of a face appearing in an image and creating a tamper-evident record of the verification.

The project combines computer vision, reverse image search, independent face verification, cryptographic hashing, and blockchain technology.

Given an input image containing a single face, the system:

1. Detects and encodes the face.
2. Performs a reverse image search to discover possible online sources.
3. Independently verifies whether the face found in the selected source matches the input face.
4. Generates a deterministic SHA-256 fingerprint of the verification evidence.
5. Stores the fingerprint on a local Ethereum-compatible blockchain.
6. Recomputes the fingerprint and compares it with the blockchain record to detect tampering.

The complete process can be executed using a single command.

```bash
python -m src.pipeline data/input/single_face.jpg
```

---

## Project Objective

The main objective of this project is to create a verification workflow where the result is not only based on visual similarity, but is also supported by a cryptographic integrity check.

The project answers two questions:

1. Does the face in the discovered online source match the face in the input image?
2. Has the evidence used to establish that match remained unchanged after verification?

The first question is addressed using facial encodings and face-distance comparison.

The second question is addressed using SHA-256 hashing and blockchain storage.

# Core Workflow

## Step 1: Face Detection and Encoding

**File:** `src/face_stage.py`

The first stage processes the input image using the `face_recognition` library.

The system:

- Validates the input image.
- Loads the image.
- Detects faces.
- Ensures that exactly one face is present.
- Generates a numerical face encoding.

The system rejects images when:

- The image does not exist.
- The image cannot be loaded.
- No face is detected.
- Multiple faces are detected.

Run this stage independently:

```bash
python -m src.face_stage data/input/single_face.jpg
```

---

## Step 2: Reverse Image Search

**File:** `src/search_stage.py`

The second stage searches the web for visually related images and possible source webpages.

The system uses SerpApi to access Google Lens results.

The process is:

1. The input image is submitted to the configured search service.
2. Search results are retrieved.
3. Candidate webpages are extracted.
4. The available candidates are displayed.
5. The user selects the relevant candidate.
6. The selected candidate is stored for the next stage.

The search result is saved to:

```text
data/output/search_result.json
```

Run this stage independently:

```bash
python -m src.search_stage data/input/single_face.jpg
```

### Dynamic Candidate Discovery

The project does not hardcode a particular person, website, or candidate URL.

The source used for verification is obtained from the live reverse image search results.

This makes the workflow applicable to different input images and different online sources.

### Browser Behavior

The project intentionally does not automatically open Google Lens in a browser when automated search fails.

The browser fallback is disabled so that the complete workflow remains controlled by the application.

---

## Step 3: Independent Face Verification

**File:** `src/verify_match.py`

The third stage independently verifies the selected candidate source.

The candidate URL is obtained from the result generated by Step 2.

The system then:

1. Loads the original input face independently.
2. Fetches the candidate webpage.
3. Discovers images from the webpage.
4. Uses Playwright to render dynamic webpage content.
5. Handles dynamically loaded and lazy-loaded images.
6. Downloads candidate images.
7. Detects faces in the downloaded images.
8. Generates face encodings for detected faces.
9. Compares the candidate encodings with the original encoding.
10. Selects the closest face match.

The current face-distance threshold is:

```text
0.45
```

A face distance below this threshold is treated as a successful face match.

The result is saved to:

```text
data/output/verification_result.json
```

Run this stage independently:

```bash
python -m src.verify_match data/input/single_face.jpg
```

---

# Step 4: SHA-256 Evidence Fingerprinting

**File:** `src/fingerprint.py`

After successful face verification, the project creates a structured evidence record.

The evidence record contains information such as:

- Matched source URL
- Matched image URL
- SHA-256 hash of the matched image
- Face distance
- Verification threshold
- Verification status
- Search engine
- Search method
- Timestamp

The evidence is converted into a deterministic canonical JSON representation.

The canonical representation is then hashed using SHA-256.

This produces a fixed 256-bit fingerprint representing the verified evidence.

The important idea is:

```text
Evidence Record
      |
      v
Canonical JSON
      |
      v
SHA-256
      |
      v
Evidence Fingerprint
```

The generated files are:

```text
data/output/evidence_record.json
data/output/fingerprint.json
```

Run this stage independently:

```bash
python -m src.fingerprint
```

# Step 5: Blockchain Storage

## Blockchain Used

The project uses a **local Hardhat Ethereum-compatible blockchain**.

### Blockchain Stack

| Component | Technology |
|---|---|
| Blockchain Network | Hardhat Local Network |
| Smart Contract | Solidity |
| Blockchain Client | Web3.py |
| RPC Endpoint | `http://127.0.0.1:8545` |
| Contract | `FingerprintRegistry.sol` |

The blockchain is used to store the cryptographic fingerprint of the verified evidence.

The original image is not stored on the blockchain.

Instead, the project stores the SHA-256 fingerprint and reference information. This creates a compact integrity record that can be checked later.

---

## Smart Contract

**File:**

```text
contracts/FingerprintRegistry.sol
```

The smart contract stores:

- Fingerprint hash
- Evidence/source reference
- Submitter blockchain address
- Blockchain timestamp

It also provides functions to retrieve individual records and the latest record.

---

## Start the Hardhat Blockchain

Open a separate terminal and run:

```bash
npx hardhat node
```

Keep this terminal running.

The local blockchain is available at:

```text
http://127.0.0.1:8545
```

---

## Deploy the Smart Contract

From the project directory:

```bash
npx hardhat run scripts/deploy.js --network localhost
```

Deployment information and the contract ABI are written to:

```text
data/output/deployment.json
data/output/FingerprintRegistry.abi.json
```

---

## Store the Fingerprint

After generating the fingerprint, run:

```bash
python -m src.blockchain_upload
```

This stage:

1. Reads the generated fingerprint.
2. Connects to the Hardhat blockchain.
3. Sends the fingerprint to the smart contract.
4. Waits for the blockchain transaction.
5. Retrieves the latest blockchain record.
6. Compares the stored fingerprint with the local fingerprint.
7. Reports whether the blockchain verification succeeded.

---

# Step 6: Blockchain Re-verification

**File:** `src/blockchain_verify.py`

The final stage checks whether the evidence has changed after it was stored on the blockchain.

The process is:

```text
Current Evidence
      |
      v
Recompute SHA-256
      |
      v
Local Fingerprint
      |
      | Compare
      v
Blockchain Fingerprint
      |
      +-------------------+
      |                   |
      v                   v
   MATCH             DIFFERENT
      |                   |
      v                   v
  VERIFIED          TAMPER DETECTED
```

Run this stage independently:

```bash
python -m src.blockchain_verify
```

If the fingerprints match:

```text
Result:
VERIFIED
```

If they are different:

```text
Result:
TAMPER DETECTED
```

# Complete Pipeline

The complete six-step process is connected through:

```text
src/pipeline.py
```

Run the entire system using:

```bash
python -m src.pipeline data/input/single_face.jpg
```

The pipeline executes:

```text
Step 1  Face Detection and Encoding
Step 2  Reverse Image Search
Step 3  Independent Face Verification
Step 4  SHA-256 Evidence Fingerprinting
Step 5  Blockchain Storage
Step 6  Blockchain Re-verification
```

A successful execution ends with:

```text
STATUS: SUCCESS

All 6 steps completed successfully.
The local hash and chain hash were compared and verified
HENCE, RECORD WAS NOT TAMPERED
```

This confirms that the evidence fingerprint generated locally matches the fingerprint stored on the blockchain.

# Tamper Detection Demonstration

The project can demonstrate how a change in the evidence affects the verification result.

The original evidence is fingerprinted and stored on the blockchain.

If the evidence is modified later, the SHA-256 fingerprint generated from the modified evidence will be different.

The blockchain still contains the original fingerprint.

Therefore:

```text
Original Evidence
      |
      v
Original SHA-256
      |
      v
Blockchain
      |
      |
Evidence Modified
      |
      v
New SHA-256
      |
      v
Compare
      |
      v
TAMPER DETECTED
```

This demonstrates the role of blockchain as an integrity anchor for digital evidence.

# Key Technical Concepts

## Face Encoding

A detected face is converted into a numerical representation called a face encoding.

The encoding is used to compare the input face with faces discovered in candidate images.

## Face Distance

The project compares facial encodings using face distance.

A lower distance indicates greater similarity.

The current matching threshold is:

```text
0.45
```

## Reverse Image Search

Reverse image search is used to discover possible online sources for the input image.

The project does not assume a particular website or person in advance.

## SHA-256

SHA-256 converts the evidence record into a fixed-length cryptographic fingerprint.

A change in the evidence produces a different fingerprint.

## Blockchain Integrity

The blockchain stores the fingerprint independently of the local evidence.

This allows the project to later determine whether the evidence has remained unchanged.

# Known Limitations

## 1. Local Blockchain

The current implementation uses a local Hardhat blockchain.

It is intended for development, testing, and demonstration rather than production deployment.

Restarting the Hardhat node resets its local blockchain state. The contract must therefore be deployed again when the local chain is reset.

## 2. Reverse Image Search Dependency

Search results depend on the external search service, indexed web content, API availability, and API limits.

## 3. Face Verification Threshold

The current face-distance threshold is `0.45`.

Lighting, pose, resolution, image quality, compression, and facial angle can affect face distance.

## 4. Single-Face Input

The input image must contain exactly one detectable face.

## 5. Webpage Accessibility

Some websites may block automated requests, use anti-bot protection, require authentication, or load content in ways that prevent complete image discovery.

## 6. Candidate Selection

The reverse image search stage presents candidates and requires the user to select the relevant candidate.

## 7. Instagram Availability

The sample person used for testing does not have a public Instagram profile.

Therefore, Instagram matches may not appear in the reverse image search results.

This is a limitation of publicly available and indexed search data rather than a limitation of the face verification algorithm.

## 8. Blockchain Storage

The original image is not stored on the blockchain.

Only the cryptographic fingerprint and reference information are stored.

## 9. Production Deployment

The current blockchain configuration uses a local Hardhat network and is intended for demonstration and development.
